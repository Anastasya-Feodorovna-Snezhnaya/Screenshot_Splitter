# GitHub 协作交互要求

本文档记录使用 GitHub 协作工具参与 Screenshot Splitter 开发时必须遵守的交互约束。

## 1. 语言要求

在能够使用现代汉语准确表达的情况下，优先使用现代汉语进行项目协作。

- 源代码注释使用现代汉语。
- Git commit 提交消息使用现代汉语。
- 与维护者讨论开发任务、实现结果和变更说明时，优先使用现代汉语。
- API、类名、函数名、变量名等程序标识符仍遵循代码本身的命名约定，不要求为了中文化而修改标识符。
- 必须使用技术术语时，可以保留必要的英文术语，例如 API、GitHub、Windows、PNG、Undo、Redo 等。

## 2. 分支与提交

- 功能开发应在功能分支上进行，不直接在 `master` 分支上开发功能。
- 每次提交应具有清晰、单一且可理解的变更目的。
- commit 消息使用现代汉语，简明说明本次提交完成的变更。
- 提交前应检查代码与受影响的开发文档是否同步。

## 3. Pull Request 约束

**未经仓库维护者（仓库所有者）明确沟通和确认，不得主动创建 Pull Request。**

当前阶段的协作要求是：

- 可以自主创建功能分支并在分支上迭代代码。
- 可以自主提交代码和同步相关开发文档。
- 不得因为认为某项功能已经完成，就自行发起 PR。
- 只有在与维护者沟通并获得明确确认后，才可以创建 PR。
- 自主发起的 PR 在当前阶段暂不处理，因此不要主动创建。

## 4. 变更完成前的检查

完成一次功能迭代后，应至少检查：

1. 用户需求是否已经落实到代码。
2. 用户可观察的功能变化是否已经同步到 `功能需求.md`。
3. 实现细节变化是否影响其他开发文档。
4. commit 消息和新增源码注释是否遵循现代汉语要求。
5. 是否存在未经确认就创建 PR 的行为。
6. 如果修改的是完整源文件，应先确认当前文件包含近期已经完成的功能，再提交完整文件内容，避免使用旧版本文件覆盖已有实现。
7. 对核心 UI 等已有功能进行重构时，应优先确认功能入口、状态更新和事件连接没有因重构遗漏。

## 5. 完整源文件修改的防回退原则

当工具需要通过“完整文件替换”的方式修改源文件时，不能只根据较早版本的文件内容进行修改。应先读取目标分支当前版本，确认近期提交已经加入的功能，再在当前版本基础上进行修改。

尤其需要注意以下情况：

- 类外 monkey patch、动态注册或文件末尾追加的代码容易在整文件更新时被遗漏。
- 核心 UI 功能不应依赖容易被整文件替换意外删除的类外补丁。
- 修改完成后应检查本次变更是否意外删除近期已经完成的按钮、快捷键、异常处理、状态更新等功能。
- 如果发现文件替换导致已有功能回退，应立即修复，而不是把回退当作新的功能变更继续向前开发。

本次开发中曾出现主窗口“重置”和“设置”按钮因后续完整文件修改遗漏类外 monkey patch 而消失的问题。修复后将这两个核心 QAction 直接放入 `MainWindow._build_ui()`，并将 `edit_settings()` 恢复为正常类方法，以降低类似回退风险。

## 6. 代码与文档同步

项目开发过程中，代码和文档应保持同步。实现细节发生变化时，应同步更新对应开发文档；用户需求发生变化时，才修改 `功能需求.md`。

本项目特别要求：核心界面结构、模块职责、公开接口和重要实现经验不能只依赖聊天记录，应沉淀到相应开发文档中。

本规则属于项目开发与维护过程中的协作约束；后续如果维护者明确修改这些要求，应以新的明确要求为准。
