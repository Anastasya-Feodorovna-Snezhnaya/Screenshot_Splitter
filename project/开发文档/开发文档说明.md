# 开发文档说明

本目录用于记录 Screenshot Splitter 的需求、约束以及当前实现状态。顶层 `README.md` 面向软件使用者，本目录面向项目开发与维护过程。

## 1. 文档分类与维护原则

开发文档分为两类：**长期稳定的要求/约束**与**随代码变化而更新的实现细节说明**。

### 1.1 要求与约束

这类文档描述“项目应该是什么样”，是后续实现和验证的行为基准。

- 需求、用户操作方式或产品约束没有发生变化时，不应因为代码重构、实现方式变化或个人偏好而修改。
- 只有在需求或约束本身发生变化时，才修改对应内容。
- 代码不能为了适应当前实现而反向修改需求文档。

当前属于这一类的主要是：

### `功能需求.md`

从用户功能和操作流程出发，记录软件应该提供什么功能，以及每项功能的具体行为、操作方式和预期结果。

功能实现发生变化时，应首先判断是否只是实现细节变化。如果用户可观察的功能和约束没有变化，则不修改需求；如果用户功能发生变化，则同步修改对应需求。

### 1.2 实现细节说明

这类文档描述“项目当前实际上怎么实现”，属于代码现状的辅助说明。

- 代码实现框架、模块职责、公开接口、日志系统等发生变化时，应及时更新。
- 这类文档不是长期不变的规范，不能因为“以前写过”就继续保留已经过时的实现描述。
- 如果实现细节与需求发生冲突，应优先识别为实现未满足需求，而不是直接修改需求文档。

当前属于这一类的主要是：

### `项目结构.md`

记录当前项目目录结构、模块职责、模块之间的关系以及主要数据流。

新增、删除、移动文件或目录，或者模块职责发生明显变化时，应同步更新本文件。

### `公开接口.md`

记录当前模块对其他模块提供的公开类、函数、方法、属性、信号等接口，并说明用途、参数和重要行为。

新增公开接口、删除公开接口、修改公开接口签名或重要行为时，应同步更新本文件。

如果某个接口的行为逻辑复杂到需要较长注释才能说明，并且该行为对模块协作或后续维护具有重要意义，则应优先将这部分稳定的接口行为记录到本文件或对应设计文档中，而不是只依赖源码注释。源码注释主要用于补充局部实现细节、设计原因和容易误解的代码。

### `调试日志.md`

记录当前版本调试日志系统的实际分类、字段、命令行参数、记录范围和排查方法。

日志系统的实现方式、记录字段、分类或启用方式发生变化时，应同步更新本文件。

### `项目进度.md`

记录当前项目已经完成、正在开发和计划开发的工作，用于反映实际开发状态。

**每次完成或修改项目功能后，都应检查并同步更新本文件。** 文档中的“已完成”应尽量表示已经实际实现并经过相应验证的功能；仅完成代码但尚未完成实际验证的内容，应明确标注验证状态。

## 2. 文档更新规则

项目开发过程中，代码和文档应保持同步，但不同文档的同步原则不同：

| 发生的变化 | 文档处理 |
| --- | --- |
| 用户功能、操作流程或产品约束发生变化 | 修改 `功能需求.md`，因为要求发生了变化 |
| 仅实现方式、代码框架或内部机制发生变化 | 更新对应的实现细节文档，不修改 `功能需求.md` |
| 项目目录、文件或模块职责发生变化 | 更新 `项目结构.md` |
| 新增、删除或修改公开接口及其重要行为 | 更新 `公开接口.md` |
| 调试日志分类、字段、记录范围或启用方式发生变化 | 更新 `调试日志.md` |
| 任意开发任务状态发生变化 | 更新 `项目进度.md` |

一次变更可能同时影响多个文档。例如新增一个用户功能，通常至少需要更新 `功能需求.md` 和 `项目进度.md`；如果因此新增模块，还应更新 `项目结构.md`；如果新增其他模块需要调用的公开接口，还应更新 `公开接口.md`。

反过来，如果只是为了修复 Qt 事件路由而更换画布事件处理机制，而用户可观察行为没有变化，则不应修改 `功能需求.md`，但应更新描述当前实现框架的 `项目结构.md`、`公开接口.md` 或其他受影响的实现细节文档。

## 3. 项目开发守则

### 3.1 需求优先

实现功能时应以 `功能需求.md` 为行为基准。代码实现不能因为当前实现方便而自行改变已经确定的用户操作逻辑。

如果发现原需求不合理，需要修改功能设计，应先明确修改需求，再调整代码，最后同步项目进度。

### 3.2 预览与原图分离

预览中的缩放、平移、选择框、分割线和灰色遮罩等视觉效果属于交互层，不应直接修改原始图片像素。

导出结果应始终根据原图和编辑状态计算，而不是根据当前缩放后的预览结果生成。

### 3.3 坐标一致性

分割线和区域边界应使用原图像素坐标保存。预览缩放和平移只负责将原图坐标转换为窗口坐标。

### 3.4 模块职责清晰

新增代码应优先放入职责匹配的模块，避免为了实现单个功能不断向主窗口集中逻辑。

如果一个功能需要跨多个模块协作，应明确模块之间的接口，而不是通过隐式状态依赖实现。

### 3.5 代码与注释

源码注释和文档统一使用中文，重点解释设计意图、约束条件和容易误解的实现细节，不重复描述显而易见的代码语句。

对于重要且相对稳定的跨模块行为，应记录在开发文档中；注释不应成为唯一的行为规格说明。

### 3.6 验证状态真实

不得仅因为代码已经提交，就将功能标记为“完成”。涉及 GUI 交互的功能应进行实际运行验证；尚未验证的功能应在 `项目进度.md` 中明确记录。

## 4. 推荐开发流程

```text
明确需求
   ↓
判断是否发生需求/约束变化
   ├─ 是 → 更新《功能需求.md》
   └─ 否 → 保持《功能需求.md》不变
   ↓
设计/修改代码
   ↓
检查受影响的实现细节文档
   ├─ 项目结构是否变化？
   ├─ 公开接口是否变化？
   └─ 调试日志实现是否变化？
   ↓
运行与验证
   ↓
更新《项目进度.md》
   ↓
提交代码
```

## 5. 文档维护原则

开发文档不是开发结束后才补写的说明材料，而是开发过程中的需求基准和当前状态记录。

任何重要功能变更都应同时回答四个问题：

1. **功能需求是什么？** —— 查看或更新 `功能需求.md`；只有需求本身变化时才修改。
2. **代码结构在哪里实现？** —— 必要时更新 `项目结构.md`。
3. **模块对外提供什么接口？** —— 必要时更新 `公开接口.md`。
4. **目前开发到什么状态？** —— 更新 `项目进度.md`。

如果一个重要行为需要依靠长篇源码注释才能解释，还应进一步判断它是否属于跨模块或长期维护所需的知识；如果是，则应将其提升到对应开发文档中，避免实现知识与代码细节过度耦合。

因此，提交代码前应检查相关开发文档是否已经同步，同时避免为了描述实现现状而修改本来没有发生变化的需求和约束。
