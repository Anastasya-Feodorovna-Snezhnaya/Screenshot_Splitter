# 开发文档说明

本目录用于记录 Screenshot Splitter 的内部开发资料。顶层 `README.md` 面向软件使用者，本文件面向项目开发与维护过程。

## 1. 文档职责

### `功能需求.md`

从用户功能和操作流程出发，记录软件应该提供什么功能，以及每项功能的具体行为、操作方式和预期结果。

功能实现发生变化时，应首先检查这里的需求描述是否仍然准确；如果用户功能发生变化，应同步修改本文件对应章节。

### `项目结构.md`

记录项目目录结构、模块职责、模块之间的关系以及主要数据流。

新增、删除、移动文件或目录，或者模块职责发生明显变化时，应同步更新本文件。

### `公开接口.md`

记录模块对外提供的公开类、函数、方法、属性、信号等接口，并说明用途、参数和返回值。

新增公开接口、删除公开接口、修改公开接口签名或行为时，应同步更新本文件。

### `项目进度.md`

记录当前项目已经完成、正在开发和计划开发的工作，用于反映实际开发状态。

**每次完成或修改项目功能后，都应检查并同步更新本文件。** 文档中的“已完成”应尽量表示已经实际实现并经过相应验证的功能；仅完成代码但尚未完成实际验证的内容，应明确标注验证状态。

## 2. 文档更新规则

项目开发过程中，代码和文档应保持同步。功能、结构、接口和进度分别对应不同文档，修改时不得只更新代码而遗漏相关文档。

| 发生的变更 | 必须同步检查的文档 |
|---|---|
| 用户功能、操作流程或行为发生变化 | `功能需求.md` |
| 项目目录、文件或模块结构发生变化 | `项目结构.md` |
| 新增、删除或修改公开接口 | `公开接口.md` |
| 任意开发任务状态发生变化 | `项目进度.md` |

一次变更可能同时影响多个文档。例如新增一个用户功能，通常至少需要更新 `功能需求.md` 和 `项目进度.md`；如果因此新增模块，还应更新 `项目结构.md` 和 `公开接口.md`。

## 3. 项目开发守则

### 3.1 需求优先

实现功能时应以 `功能需求.md` 为行为基准。代码实现不能因为当前实现方便而自行改变已经确定的用户操作逻辑。

如果发现原需求不合理，需要修改功能设计，应先明确修改需求，再调整代码，最后同步项目进度。

### 3.2 预览与原图分离

预览中的缩放、平移、选择框、分割线和灰色遮罩等视觉效果属于交互层，不应直接修改原始图片像素。

导出结果应始终根据原图和编辑状态计算，而不是根据当前缩放后的预览结果生成。

### 3.3 坐标一致性

分割线和区域边界应使用原图像素坐标保存。预览缩放和平移只负责将原图坐标转换为窗口坐标。

### 3.4 模块职责清晰

新增代码应优先放入职责匹配的模块，避免为了实现单个功能不断向主窗口集中逻辑。

如果一个功能需要跨多个模块协作，应明确模块之间的接口，而不是通过隐式状态依赖实现。

### 3.5 代码与注释

源码注释和文档统一使用中文，重点解释设计意图、约束条件和容易误解的实现细节，不重复描述显而易见的代码语句。

### 3.6 验证状态真实

不得仅因为代码已经提交，就将功能标记为“完成”。涉及 GUI 交互的功能应进行实际运行验证；尚未验证的功能应在 `项目进度.md` 中明确记录。

## 4. 推荐开发流程

```text
明确需求
   ↓
更新《功能需求.md》（如需求有变化）
   ↓
设计/修改代码
   ↓
更新《项目结构.md》（如结构有变化）
   ↓
更新《公开接口.md》（如接口有变化）
   ↓
运行与验证
   ↓
更新《项目进度.md》
   ↓
提交代码
```

## 5. 文档维护原则

开发文档不是开发结束后才补写的说明材料，而是开发过程中的约束和记录。

任何重要功能变更都应同时回答四个问题：

1. **功能需求是什么？** —— 查看或更新 `功能需求.md`。
2. **代码结构在哪里实现？** —— 必要时更新 `项目结构.md`。
3. **模块对外提供什么接口？** —— 必要时更新 `公开接口.md`。
4. **目前开发到什么状态？** —— 更新 `项目进度.md`。

因此，提交代码前应检查相关开发文档是否已经同步。
